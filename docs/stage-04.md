# 4단계 — 밴드 채팅, 알림, 실시간 연결

## 만든 것

| 기능 | API | 화면 |
| --- | --- | --- |
| 실시간 연결 (채팅·알림 받기) | `GET /api/stream` (SSE) | 앱 전체에서 하나 |
| 채팅 읽기 (id 커서) | `GET /api/bands/{id}/messages?before=` | 밴드 채팅 |
| 채팅 보내기 | `POST /api/bands/{id}/messages` `{body, clientId}` | 밴드 채팅 |
| 읽음 위치 | `POST /api/bands/{id}/messages/read` `{lastId}` | 채팅을 보고 있을 때 |
| 안 읽은 채팅 수 | `/api/me/bands`, `/api/bands/{id}`의 `unreadMessages` | 밴드 카드, 상세 |
| 알림 목록 / 안 읽은 수 | `GET /api/notifications`, `GET /api/notifications/unread` | 알림 탭 |
| 읽음 / 모두 읽음 | `POST /api/notifications/{id}/read`, `/read-all` | 알림 탭 |

알림이 가는 일: 새 지원자(방장), 수락·거절(지원자), 멤버가 나감(방장), 합주 확정·시간 변경·정보 변경·취소(방장 뺀 멤버).
채팅에 남는 안내: 멤버 들어옴·나감, 합주 확정·시간 변경·취소.

### 테이블

```
chat_messages  id, band_id, sender_id(안내는 null), type(TEXT/SYSTEM), body, client_id, created_at
               (band_id, sender_id, client_id 유니크)
band_members   + last_read_message_id
notifications  id, user_id, type, title, body, link, read_at, created_at
```

## 왜 이렇게 만들었나

### 1. WebSocket 대신 SSE
- 보내기는 그냥 `POST`, 받기만 서버가 밀어 주면 된다. 받는 쪽만 필요하니 단방향인 SSE로 충분하다.
- SSE는 평범한 HTTP 요청이라 1단계의 **세션 쿠키 로그인이 그대로 통한다.** STOMP·핸드셰이크 인증을 따로 만들 필요가 없다.
- 끊기면 브라우저(`EventSource`)가 알아서 다시 붙는다. 다시 붙었을 때 화면들이 놓친 걸 다시 읽는다(`reconnect`).
- 연결을 열어 둔 채 조용하면 중간 프록시가 끊으므로 25초마다 주석 한 줄(`:ping`)을 보낸다. 이때 죽은 연결도 정리된다.
- 한계: 연결 목록이 서버 메모리에 있다. 서버를 여러 대로 늘리면 Redis pub/sub으로 다른 서버에 붙은 사람에게 전달해야 한다.

### 2. 커밋된 다음에만 보낸다
- 트랜잭션 중간에 화면으로 보내면, 그 뒤 롤백됐을 때 상대 화면에는 "없는 메시지·알림"이 남는다.
- `AfterCommit.run(...)`으로 커밋 성공 후에만 전송한다. 실패한 수락 요청이 아무것도 보내지 않는지 테스트로 확인한다.

### 3. 밴드·합주 코드는 알림을 모른다 (도메인 이벤트)
- `BandService`는 "지원이 들어왔다", `JamService`는 "합주 시간이 바뀌었다"만 발행한다.
- 누구에게 어떤 알림을 보내고 채팅에 뭐라고 남길지는 `ActivityListener` 한 곳에서 정한다.
- 리스너는 **같은 트랜잭션**에서 돈다. 수락이 롤백되면 "들어왔어요" 안내와 알림도 같이 사라진다.
- 변경이 없으면 알림도 없다. 장소를 같은 값으로 다시 저장해도 "정보가 바뀌었어요"가 가지 않는다.

### 4. 채팅 페이지는 OFFSET이 아니라 id 커서
- `OFFSET 30`으로 다음 페이지를 읽으면, 그 사이 새 메시지가 오는 순간 한 칸씩 밀려 같은 메시지가 두 번 보이거나 빠진다.
- "이 id보다 오래된 30개"(`id < before`)로 읽으면 새 메시지와 상관없이 정확하다. `(band_id, id)` 인덱스를 그대로 탄다.

### 5. 안 읽은 수 = 읽은 위치 하나
- 메시지마다 "누가 읽었나"를 저장하지 않고, 멤버마다 **마지막으로 읽은 메시지 id** 하나만 둔다.
- 안 읽은 수 = 그보다 큰 id 중 내가 보내지 않은 것. 여러 밴드를 쿼리 한 번으로 센다.
- 읽음 위치는 뒤로 가지 않고, 없는 미래 id로 앞질러 가지도 않는다(최대 id로 자름).
- 새로 들어온 멤버는 지금까지의 대화를 안 읽은 것으로 치지 않는다.

### 6. 다시 보내도 한 번만 (clientId)
- 지하철에서 보내기를 눌렀는데 응답이 안 오면, 저장됐는지 알 수 없어 다시 보내게 된다.
- 화면이 메시지마다 붙인 `clientId`가 같으면 서버는 새로 저장하지 않고 처음 것을 돌려준다.
- 화면은 보내기를 누른 순간 말풍선을 먼저 그리고("보내는 중"), 서버 응답이나 실시간 이벤트가 오면 `clientId`로 찾아 진짜 메시지로 바꾼다. 실패하면 "다시 보내기"를 띄운다.

### 7. 채팅 메시지는 알림으로 보내지 않는다
- 메시지마다 알림이 쌓이면 정작 중요한 "합주 시간이 바뀌었어요"가 묻힌다.
- 채팅은 밴드 카드의 "새 메시지 N"으로만, 알림 탭은 행동이 필요한 소식만.

## 테스트

- `ChatApiTest`: 들어옴 안내, 보내기·재전송 중복 방지, 안 읽은 수(내 것 제외), 읽음 위치(미래 id 자르기), id 커서 페이지, 멤버 아님·나간 멤버 403.
- `NotificationApiTest`: 지원·수락·거절·나감, 합주 확정·정보 변경·시간 변경·취소(방장 제외, 변경 없으면 알림 없음), 읽음·남의 알림 404.
- `StreamApiTest`: 로그인 없이 401, 열린 연결로 메시지·알림 도착, 실패한 요청은 아무것도 보내지 않음.
- 프론트: 메시지 합치기(중복·clientId 교체), 보내기 즉시 표시·실시간 수신·읽음 위치 전송, 실패 후 다시 보내기.
