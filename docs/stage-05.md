# 5단계 — 합주실 예약·정산·회비, 공연 준비

## 만든 것

| 기능 | API | 화면 |
| --- | --- | --- |
| 합주실 목록 | `GET /api/studios` | 합주실 예약 |
| 방 하루 시간표 (가격·찬 칸) | `GET /api/rooms/{id}/slots?date=` | 합주실 예약 → 방 |
| 예약 / 취소 (방장) | `POST /api/bands/{id}/bookings`, `POST /api/bookings/{id}/cancel` | 시간표, 밴드 상세 |
| 예약 목록 + 1인 정산 | `GET /api/bands/{id}/bookings` | 밴드 상세 → 합주실 |
| 정산 표시 | `PUT /api/bookings/{id}/settles/{userId}` `{paid}` | 밴드 상세 |
| 월 회비 보기 / 설정 / 납부 표시 | `GET /api/bands/{id}/dues?month=`, `PUT …/dues/settings`, `PUT …/dues/{month}/members/{userId}` | 밴드 상세 → 회비 |
| 공연 잡기 / 목록 / 상세 / 취소 | `POST·GET /api/bands/{id}/gigs`, `GET /api/gigs/{id}`, `POST …/cancel` | 밴드 상세 → 공연, 공연 화면 |
| 큐시트 저장 (버전 포함) | `PUT /api/gigs/{id}/items` `{version, items}` | 공연 화면 |
| 준비 체크리스트 | `POST/PUT/DELETE /api/gigs/{id}/checks…` | 공연 화면 |

합주실은 프로토타입과 같은 **예시 데이터 7곳**이다(`StudioSeeder`). 실제 합주실 예약 시스템과 연결되어 있지 않고,
밴드몽 사용자끼리 같은 방·같은 시간을 겹쳐 잡지 못하게 하는 데까지다.

### 테이블


## 왜 이렇게 만들었나 — 동시 수정을 막는 세 가지 방법

이 앱에는 "두 사람이 동시에 같은 것을 고치는" 상황이 세 번 나오고, 상황마다 다른 방법을 썼다.

| 상황 | 방법 | 이유 |
| --- | --- | --- |
| 마지막 빈자리에 두 명 수락 (2단계) | **비관적 잠금** (`SELECT … FOR UPDATE`, 밴드 행) | 경쟁하는 요청이 같은 밴드 안에 있다. 잠그고 다시 세면 끝. |
| 두 밴드가 같은 방 같은 시간 예약 (5단계) | **유니크 키** (`room_slots(room_id, slot_start)`) | 경쟁하는 요청이 **서로 다른 밴드**라 밴드 행 잠금으로는 못 막는다. 잠글 "방 행"을 따로 두는 대신, 시간 칸마다 한 줄을 넣고 DB가 중복을 거절하게 했다. |
| 두 멤버가 같은 큐시트 저장 (5단계) | **낙관적 잠금** (`@Version`) | 큐시트는 몇 분씩 화면에서 고친 뒤 저장한다. 그동안 잠가 둘 수는 없다. 대신 "내가 불러온 버전"을 함께 보내고, 그 사이 누가 저장했으면 409로 알려 준다. |

### 1. 예약 겹침 — 확인은 친절하게, 최종 판정은 유니크 키
- 먼저 그 시간 칸이 찼는지 조회해서 "그 시간은 이미 예약돼 있어요"로 안내한다(대부분 여기서 걸린다).
- 조회와 저장 사이에 다른 밴드가 끼어들면 `room_slots` INSERT가 유니크 키에 걸리고, 이를 잡아 "방금 다른 밴드가 예약했어요"(409)로 바꾼다.
  예약 행·정산 행까지 한 트랜잭션이라 함께 롤백된다.
- 4시간 예약 = 칸 4줄. 21시~23시 예약과 22시 1시간 예약은 22시 칸에서 부딪힌다.
- 취소하면 칸을 지워서 다른 밴드가 바로 잡을 수 있다. 예약 기록은 상태만 바꿔 남긴다.
- `BookingApiTest`가 두 스레드로 같은 방·시간을 동시에 예약해 정확히 한 밴드만 성공하는지 확인한다.

### 2. 큐시트 — 내가 본 버전으로 저장
- 저장 요청에 `version`을 함께 보내고, 지금 버전과 다르면 409 "다른 멤버가 먼저 큐시트를 고쳤어요".
- 둘 다 같은 순간에 확인을 통과해도, JPA `@Version`이 `UPDATE … WHERE version = ?`로 한 번 더 막는다(그 예외도 409로 바꿈).
- 화면은 409를 받으면 "최신으로 불러오기"를 띄운다. 말없이 덮어쓰는 일은 없다.
- 체크리스트는 큐시트 버전에서 뺐다(`@OptimisticLock(excluded = true)`). 누가 "케이블 챙기기"를 체크했다고 큐시트 저장이 충돌하면 안 된다.
- 큐시트는 줄 단위가 아니라 **통째로** 저장한다. 순서 바꾸기·여러 줄 수정이 한 번에 일어나는 화면이라 그쪽이 단순하고, 버전 하나로 충돌을 판단할 수 있다.

### 3. 돈은 "그때 금액"을 남긴다
- 예약 금액·1인 몫은 예약할 때 계산해 저장한다. 나중에 합주실 가격이 바뀌거나 멤버가 늘어도 이미 정산 중인 금액은 그대로다.
- 1인 몫은 100원 단위 올림(38,000원 ÷ 4명 = 9,500원). 화면 미리 보기도 같은 계산을 쓴다.
- 회비 납부 기록에도 그 달 금액을 남긴다. 회비를 3만 원에서 4만 원으로 올려도 지난달 기록은 3만 원이다.
- 정산·회비는 "냈다고 표시"만 한다(실제 송금 연동 없음). 본인은 자기 것만, 방장은 누구 것이든 바꿀 수 있고, 누가 표시했는지 남긴다.

### 4. 시간 칸과 새벽 영업
- 영업시간을 `10~26`처럼 24를 넘는 숫자로 둔다(26 = 다음 날 새벽 2시). 하루 시간표를 한 줄로 그릴 수 있고, "밤 10시 이후 할인"도 `hour >= 22`로 끝난다.
- 칸의 실제 시각은 `그 날짜 0시(한국) + hour 시간`으로 계산해 UTC로 저장한다.

### 5. 합주 → 합주실 연결
- 합주 상세에서 "이 시간으로 합주실 잡기"를 누르면 날짜·시작·길이를 채운 채 예약 화면이 열리고, 예약에 합주 id가 붙는다.

## 테스트

- `BookingApiTest`: 시간표·밤 할인, 예약·칸 막힘·1인 몫, 겹치는 시간 409, 방장만·영업시간·지난 시간,
  정산(본인/방장), 채팅 안내·알림, 취소 후 다른 밴드 예약, **두 밴드 동시 예약 → 한 밴드만**.
- `DuesApiTest`: 회비 없음 409, 방장만 설정, 본인/방장 표시, 두 번 눌러도 한 번, 달 형식·범위, 남의 밴드 403.
- `GigApiTest`: 공연 잡기(초안·준비 목록·알림·안내), 오래된 버전 409, 체크해도 버전 그대로, 검사·취소, **같은 버전 동시 저장 → 한 명만**.
- 프론트: 1인 몫 계산, 큐시트 시각 계산·순서 바꾸기, 저장 409 → 최신으로 불러오기.
